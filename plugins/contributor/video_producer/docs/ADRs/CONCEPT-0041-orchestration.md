# CONCEPT-0041 — Video Quality Enhancement Orchestration

**Status:** Proposed  
**Date:** 2026-09-13  
**Deciders:** Claude Haiku 4.5, Shumway (CorvinOS maintainer)

## Executive Summary

The current Video Producer Skill 2.0 ships videos with **no quality control, no encoding optimization, and no asset validation**. This concept introduces a **8-dimensional quality model** with orchestrated Workers:

1. **Input Validation** (asset deep analysis, contradiction detection)
2. **Scene Quality Prediction** (LLM → confidence scores)
3. **Adaptive Encoding** (resolution/bitrate/codec tuned per scene type)
4. **Color Processing** (normalization, grading, colorspace management)
5. **Performance Optimization** (GPU acceleration, parallel rendering, caching)
6. **Per-Scene Feedback Loop** (user approval, learning integration)
7. **Output Verification** (quality metrics, artefact detection, adaptive fallback)
8. **Dashboard Observability** (real-time metrics, convergence tracking)

**Deliverables:**
- **CONCEPT-0041** (this document) — reusable pattern for quality orchestration
- **ADR-0702** (input validation strategy)
- **ADR-0703** (adaptive encoding + codec selection)
- **ADR-0701** (color processing pipeline)
- **ADR-0702** (performance & GPU acceleration)
- **ADR-0703** (per-scene feedback + learning loop integration)

## Context

### Current State

The Video Producer Skill 2.0 (Phase 1) generates videos that:
- ✅ Produce watchable output (LLM storyboard → screenshots → FFmpeg assembly)
- ❌ Have **no quality targets** (no resolution, bitrate, or codec config)
- ❌ Use **hardcoded FFmpeg defaults** (usually 1280×720 H.264 baseline)
- ❌ Skip **asset validation** (screenshots taken as-is, no contradiction/hallucination check)
- ❌ Ignore **encoding optimization** (single FFmpeg pass, no scene-adaptive tuning)
- ❌ Have **no color consistency** (different tools produce different color spaces)
- ❌ Lack **performance tuning** (CPU-bound, no GPU, no parallelization)
- ❌ Provide **no user feedback on quality** (fire-and-forget, no per-scene review loop)

### Problem Statement

Users see:
1. **Inconsistent visual quality** across scenes (grainy→crisp→over-exposed transitions)
2. **Bloated file sizes** (H.264 baseline codec, unnecessary bitrate)
3. **Slow production times** (sequential FFmpeg calls, CPU bottleneck)
4. **No recourse on poor output** (complete video or nothing; no per-scene approval)
5. **Hallucinated content** (LLM-generated screenshots not validated)
6. **No quality metrics** (how to tell if a 50MB vs 100MB video is "better"?)

### Root Causes

| Dimension | Root Cause | Impact | ADR |
|---|---|---|---|
| **Input** | Screenshots generated by LLM, no verification | Hallucination, contradictions | ADR-0702 |
| **Encoding** | Hard-coded `ffmpeg -c:v libx264 -crf 23` for all scenes | Suboptimal quality/size trade-off | ADR-0703 |
| **Color** | No colorspace management (sRGB vs BT.709 vs BT.2020) | Color banding, shifts between scenes | ADR-0701 |
| **Performance** | Single-threaded FFmpeg, no GPU, no caching | 30+ min for 5-min video on CPU | ADR-0702 |
| **Feedback** | No per-scene approval; "all or nothing" UX | Users can't fix individual bad scenes | ADR-0703 |

---

## The Method: 8-Dimensional Quality Orchestration

### Thesis: "Quality is a Control Plane"

A Skill 2.0 system (Orchestrator + 5 Worker Skills) treats quality as a **first-class orchestration concern**, not an afterthought. Every scene is measured, every encoding is adaptive, every asset is verified.

### Antithesis: "Keep It Simple"

Adding complexity → more code, more failure modes, more things to tune. Just lock quality settings once and move on. Cost: perpetual user complaints about bloated/blurry videos.

### Synthesis: **Hybrid Approach**

- **Immutable Quality Baselines** (never change) — Input validation gates, output verification gates, fail-closed design
- **Learnable Encoding Parameters** — per-scene-type tuning via feedback loop (ADR-0314 integration)
- **Operator Control Panel** — preset configs (YouTube/LinkedIn/Presentation/Archive) + manual override
- **Progressive Rollout** — Phase 1: Input validation + baseline encoding; Phase 2: Adaptive encoding + feedback loop; Phase 3: GPU acceleration + dashboard

## 8-Dimensional Model

### 1. **Input Validation** (Asset Deep Analysis)

**What:** Every screenshot/image asset is analyzed BEFORE rendering.

**Checks:**
- ✅ **Contradiction Detection** — screenshot shows feature X but storyboard scene says Y (LLM mismatch)
- ✅ **Hallucination Detection** — screenshot shows non-existent UI elements or broken layouts
- ✅ **Resolution Validation** — min 720p, max 4K (user-configurable)
- ✅ **Color Space Detection** — sRGB vs P3 vs BT.709 (fail-closed: convert to sRGB)
- ✅ **Artifact Detection** — aliasing, compression artefacts, watermarks (FAIL-CLOSED: reject)
- ✅ **Dynamic Range Analysis** — histogram skewness, blown highlights/crushed blacks

**Inputs:** Screenshot file, expected storyboard description, scene metadata  
**Outputs:** `AssetValidationResult` (pass/fail, issues list, recommended corrections)  
**Failure Mode:** Reject and propose scene retry (learning signal for next iteration)  

**LDD Metric:** Precision (false-positive rate <5%), Recall (catch 90%+ real hallucinations)

**ADR:** ADR-0702 — Input Validation Strategy

---

### 2. **Scene Quality Prediction** (Pre-Flight Confidence)

**What:** Before rendering, predict the output quality of each scene.

**Signals:**
- Scene type (title/narration/screenshot/animation/screencast)
- Asset validation results (did checks pass?)
- TTS quality (if voice narration)
- Screenshot complexity (object count, color variance)
- Target resolution vs input resolution (upscaling needed?)

**Model:** Lightweight LLM (Opus or Haiku) → confidence score (0–1)

**Outputs:** Per-scene confidence, warnings, adaptive encoding hints

**Failure Mode:** Confidence <0.6 → auto-escalate to user for review

**LDD Metric:** Calibration error (predicted confidence vs actual user satisfaction)

**ADR:** ADR-0703 (embedded in encoding section)

---

### 3. **Adaptive Encoding** (Codec & Bitrate Selection)

**What:** Choose video codec, resolution, bitrate per scene type, NOT globally.

**Encoding Decision Table:**

| Scene Type | Input Type | Codec | Resolution | Bitrate | Preset | Why |
|---|---|---|---|---|---|---|
| **Title** | Static image | H.265 | 1080p | 2–4 Mbps | medium | High quality needed, low motion → H.265 efficient |
| **Narration** | Screenshot + TTS | H.264 | 1080p–1440p | 4–8 Mbps | medium | Balanced quality/speed, compatible |
| **Screencast** | Moving/interactive | H.264 | 1440p–2160p | 8–16 Mbps | fast | Motion needs bitrate, H.264 < H.265 for speed |
| **Animation** | Generated/AI | H.265 | 1080p–2160p | 6–12 Mbps | slow | Synthetic content compresses well → H.265 |
| **Composite** | Multiple elements | H.264 | 1440p | 8–10 Mbps | medium | Safest choice for mixed content |

**Config Presets** (per Skill 2.0 learning loop):

```yaml
quality_preset: "youtube"  # or "linkedin", "archive", "web", "presentation"

youtube:
  target_bitrate: 8-12 Mbps (1080p), 20-25 (4K)
  codec: H.264 (compatibility), fallback H.265 (if client supports)
  colorspace: BT.709
  profile: baseline (wide compatibility)

archive:
  target_bitrate: 15-25 Mbps
  codec: H.265
  colorspace: BT.2020 (10-bit, if source supports)
  profile: main10 (HDR-ready)

presentation:
  target_bitrate: 4-8 Mbps
  codec: H.264
  colorspace: sRGB
  profile: baseline
  
linkedin:
  target_bitrate: 8 Mbps (max, platform SLA)
  codec: H.264
  colorspace: BT.709
  resolution: 1080p (platform recommends)
```

**Learning Loop:** User feedback ("this scene is too blurry/large") → optimizer tunes per-scene-type bitrate for next job

**LDD Metric:** Filesize per minute (target: 20–40 MB/min for YouTube)

**ADR:** ADR-0703 — Adaptive Encoding & Codec Selection

### 4. **Color Processing Pipeline**

**What:** Normalize, grade, and validate color space across all scenes.

**Pipeline Stages:**

1. **Input Colorspace Detection** — examine EXIF/metadata, infer from content
2. **Conversion to Working Space** — convert all to sRGB (default) or BT.709 (video)
3. **Normalization** — equalize brightness/contrast across scenes (avoid sudden jumps)
4. **Optional Grading** — apply LUT or color correction (preset list)
5. **Output Conversion** — convert to target output colorspace (BT.709 for video)

**Fail-Closed Design:**
- If colorspace conversion fails → reject scene (don't guess)
- If histogram analysis shows blown highlights/crushed blacks → warn (not error)
- If scene colors clash with previous → interpolate a transition (fade or color match)

**Config:**

```yaml
color:
  input_detection: auto  # detect from EXIF, or "sRGB" / "p3" / "bt709"
  working_space: sRGB
  normalization:
    enabled: true
    method: histogram_matching  # or "curve_fitting"
    target_luminance: 50  # target average brightness (0-100)
  grading:
    preset: none  # or "warm", "cool", "vintage", "cinematic"
  output_colorspace: BT.709  # for video
  output_profile: baseline  # or "wide_gamut"
```

**LDD Metric:** Color consistency score (frame-to-frame chrominance variance)

**ADR:** ADR-0701 — Color Processing Pipeline

### 5. **Performance & GPU Acceleration**

**What:** Eliminate CPU bottlenecks via parallelization and hardware encoding.

**Optimizations:**

1. **GPU Hardware Encoding** (NVIDIA CUDA / Intel QSV)
   - H.264 NVENC (2–3x faster than libx264 on GPU)
   - H.265 NVENC (if available, best compression)
   - Fallback to CPU if GPU unavailable

2. **Scene-Level Parallelization**
   - Generate TTS audio for all scenes in parallel (thread pool)
   - Render all screenshot assets in parallel (Playwright browsers)
   - Encode all scene segments in parallel (FFmpeg workers)
   - Multiplex final output (single-threaded, sequential)

3. **Scene Caching**
   - Cache rendered screenshots (TTS + graphics reused)
   - Cache encoded intermediate videos (if scene unchanged between runs)
   - Cache color LUTs (pre-computed for each preset)

4. **Memory Management**
   - Streaming encode (process in chunks, not all in RAM)
   - Intermediate cleanup (delete temp files after each scene)

**Config:**

```yaml
performance:
  gpu_enabled: true
  gpu_device: "cuda"  # or "qsv", "videotoolbox" (macOS)
  hardware_encoding:
    h264: true
    h265: true
  parallelization:
    tts_workers: 4
    screenshot_workers: 3
    encode_workers: 2
  caching:
    screenshot_cache: true
    encoded_segments: false  # enable for iterative workflows
```

**LDD Metric:** Time per minute of video (target: <30s for 1-min video with GPU)

**ADR:** ADR-0702 — Performance & GPU Acceleration

### 6. **Per-Scene Feedback & Learning Loop**

**What:** User reviews video, approves/rejects individual scenes, trains the system.

**UX Workflow:**

```
Video Produced
  ↓
Operator Views Console Panel
  ↓
For Each Scene:
  [Preview] [✓ Approve] [✗ Reject] [Edit]
  ↓ (if Reject)
  Auto-escalate to LLM for scene rewrite
  ↓ (if Edit)
  Manual storyboard tweak + re-render scene
  ↓ (Approve or final Reject)
  Emit FeedbackEvent (quality score, reason)
  ↓
Learning Loop Reads FeedbackEvents
  ↓
Optimizer Adjusts:
  - Scene quality confidence threshold
  - Per-scene-type encoding parameters
  - Color normalization targets
  - Asset validation strictness
  ↓
Next Job Uses Tuned Config
```

**Feedback Types:**

```python
@dataclass
class SceneQualityFeedback:
    scene_id: str
    job_id: str
    feedback_type: Literal["too_blurry", "too_compressed", "color_wrong", "hallucination", "good", "excellent"]
    confidence: float  # 0–1, user's confidence in the feedback
    reason: str  # free-text explanation (audit-only, never used for learning)
    timestamp: datetime
```

**Learning Signals:**
- Avg feedback score per scene type (title/narration/screenshot)
- Blurriness complaints → increase bitrate for that scene type
- Compression complaints → use H.265 instead of H.264
- Color issues → tighten normalization settings
- Hallucination → increase input validation strictness

**LDD Metric:** Mean feedback score per scene type (target: >0.8 after 10 iterations)

**ADR:** ADR-0703 — Per-Scene Feedback & Learning Integration

---

### 7. **Output Verification & Adaptive Fallback**

**What:** Validate the rendered video before serving; fall back gracefully on failure.

**Checks:**
- ✅ File exists and is readable (basic sanity)
- ✅ Codec supported by target platform (validate profile, bitrate, resolution)
- ✅ Metadata integrity (duration, bitrate, frame rate)
- ✅ Artefact detection (encoding errors, sync issues)
- ✅ Quality metrics (frame size, bitrate consistency)

**Adaptive Fallback (if quality fails):**

```
High-Quality Render Failed (e.g., H.265 on old platform)
  ↓
Retry with Lower Settings (H.264, lower bitrate)
  ↓
If Still Fails:
  Emit AdaptiveQualityEvent (quality degradation, reason)
  Return Best Effort (lower quality, but working)
```

**LDD Metric:** Fallback rate (target: <1% of jobs)

**ADR:** ADR-0703 (embedded in encoding section)

## When to Use / When NOT to Use

### ✅ Use This Pattern When:

1. **Output quality is user-facing** (videos for external audience)
2. **You can afford per-scene validation** (asset deep analysis cost)
3. **Users will review and provide feedback** (per-scene approval loop)
4. **Hardware is available** (GPU for acceleration; CPU-only fallback supported)
5. **Platform constraints matter** (YouTube vs LinkedIn vs archive → different presets)

### ❌ Do NOT Use When:

1. **Speed matters more than quality** (use Phase 1 baseline encoding)
2. **No GPU available and CPU time is precious** (skip hardware acceleration section)
3. **Users won't review output** (skip per-scene feedback loop; keeps unlearned)
4. **All output is identical** (no scene-adaptive encoding; apply one preset globally)

## Load-Bearing Invariants

### 1. **Input Validation is FAIL-CLOSED**
- Invalid asset → reject scene, don't guess
- Contradiction detected → escalate to human, don't render anyway
- Audit event logged (GDPR compliance)

### 2. **Encoding Baselines are IMMUTABLE**
- User can choose preset (YouTube/Archive/Presentation) — that's tunable
- But the baseline safety constraints (min bitrate, max artifacts) are locked
- Optimizer tunes WITHIN those constraints, never outside

### 3. **Color Processing Conversions are VERIFIED**
- Colorspace conversion fails → reject, don't ship unconverted
- Histogram analysis shows clipping → warn but allow (user can reject)

### 4. **Learning Loop is GATED**
- Feedback must pass validation before it affects next job
- Malicious feedback (e.g., "everything is bad") has low weight initially
- Operator can inspect feedback + override before applying

### 5. **Observability is COMPLETE**
- Every quality decision logged (audit chain)
- Dashboard shows real state (not estimated/cached metrics)
- Export reports include full traceability (scene → feedback → optimizer delta)

## Implementation Phases

### Phase 1 (Weeks 1–2, ~1200 LoC)
- **Input Validation Worker Skill** (screenshot verification, contradiction detection)
- **Baseline Adaptive Encoding** (preset profiles, H.264/H.265 choice)
- **Color Space Detection** (convert to sRGB, fail-closed)
- **Console UI** (job quality metrics panel)

### Phase 2 (Weeks 3–4, ~800 LoC)
- **Per-Scene Feedback UI** (approve/reject/comment per scene)
- **Learning Loop Integration** (ADR-0314 feedback → optimizer)
- **Quality Prediction LLM** (confidence scoring)
- **Verification & Fallback** (adaptive encoding retry)

### Phase 3 (Weeks 5–6, ~600 LoC)
- **GPU Acceleration** (NVENC, Intel QSV)
- **Parallelization** (scene-level workers)
- **Caching** (screenshot + encoded segment cache)
- **Dashboard Observability** (real-time metrics, convergence tracking)

**Total Effort:** 8–12 weeks, 2,600 LoC, ~200 tests
